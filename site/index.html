x402-dotnet

Accept and pay x402 v2 HTTP payments in .NET, in EURC or USDC, with a server that never touches a signing key.

dotnet add package Atypical.X402.AspNetCore
  • .NET 10
  • x402 v2
  • Base
  • EURC · USDC
  • v0.1.1

The handshake

x402 turns HTTP 402 Payment Required into a working payment protocol. A server demands payment, the client signs, a facilitator settles, the request replays and succeeds.

This library implements x402 v2 only: CAIP-2 network identifiers such as eip155:84532, the PAYMENT-REQUIRED, PAYMENT-SIGNATURE and PAYMENT-RESPONSE headers, and protocol amounts carried as strings on the wire. No X-PAYMENT header, no x402Version: 1.

  1. 1

    The paying client calls an API through a plain HttpClient. AddX402Payment() attaches the handler that answers 402s on its behalf, within the spending limits you set.

  2. 2

    The ASP.NET Core server prices routes per asset. It holds no key and signs nothing.

  3. 3

    HTTP 402 carries a PAYMENT-REQUIRED demand listing every asset the route accepts, EURC first.

  4. 4

    An EIP-3009 signature. The client signs a transferWithAuthorization with EIP-712 typed data and replays the request with it.

  5. 5

    The facilitator verifies the authorization and settles it on-chain. It is a service you choose, not part of this library.

  6. 6

    EURC or USDC on Base. Payment moves directly from payer to the configured PayTo address.

Two currencies, offered in that order

Every reference x402 SDK, in TypeScript, Python and Go, ships one dollar stablecoin per chain. None ships a euro asset. x402-dotnet settles EURC end to end on equal footing with USDC, and offers the euro first.

Offered first

EURC

Signing, verification, settlement and spending limits, end to end. KnownAssets.EurcBaseSepolia and its Base mainnet counterpart ship verified on-chain profiles.

Equal footing

USDC

The same path, the same guarantees. A route can be priced in either asset or in both, and the payer settles in whichever it holds.

No conversion, anywhere.

Prices and client spending limits are held per asset, keyed by network and contract address, never aggregated. A shared cap across EURC and USDC would imply an exchange rate this library does not have, and a test enforces that no conversion API exists.

EURC support here is not proof that your facilitator settles it.

The x402 wire protocol never advertises settled assets: GET /supported returns scheme and network pairs only. PayingAgent --probe in the samples answers the question empirically, per facilitator, per asset. Run it before you rely on one.

MiCA compliance belongs to the issuer.

EURC is issued by Circle France SAS, licensed as an electronic money institution by the ACPR (register number 17788). x402-dotnet issues nothing, holds nothing and custodies nothing. It moves a signed authorization from a payer to a facilitator.

Why the deviation.

The original brief specified USDC alone. Going multi-asset from the start, euro first, was a deliberate decision recorded in ADR 0002.

Three packages, one version

Each layer depends only on the one below it. All three ship the same version number and full XML documentation for IntelliSense.

PackageRoleDeliberately absent
Atypical.X402.AspNetCore Accept payments. Server middleware, the imperative IX402PaymentGate, the facilitator client, an idempotency ledger. Any signing library. Any key, secret or mnemonic property.
Atypical.X402.Client Pay for requests. EIP-3009 signing, the paying DelegatingHandler, per-asset spending limits. Limits shared across currencies.
Atypical.X402.Core The wire format. Protocol types, transport codec, extension points. A transitive dependency of both, published separately for tooling. ASP.NET Core, signing, network calls, telemetry. An architecture test checks it.

The package ids carry the Atypical. prefix; the namespaces do not. You still write using X402;, using X402.Client; and using X402.AspNetCore;. The bare X402.* ids on nuget.org belong to an unrelated implementation (ADR 0004).

Quick start

No wallet needed for a first run. The samples include an offline mode where an in-process fake facilitator verifies signatures for real and settles anything well-formed.

  1. Create an API and add the server package

    dotnet new webapi -n PaidApi && cd PaidApi
dotnet add package Atypical.X402.AspNetCore

  2. Say who gets paid, on which network, in which assets

    appsettings.json

    {
  "X402": {
    "PayTo": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
    "Network": "eip155:84532",
    "Assets": [{ "Symbol": "EURC" }, { "Symbol": "USDC" }],
    "FacilitatorUrl": "https://x402.org/facilitator"
  }
}

  3. Register the pipeline and price a route

    Pricing a route in an asset the server has not configured throws from UseX402 at start-up, before the host accepts a request.

    Program.cs

    using X402.AspNetCore.DependencyInjection;
using X402.Assets;
using X402.Pricing;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddX402(builder.Configuration.GetSection("X402"));
var app = builder.Build();

app.UseX402(routes => routes.Map(
    "/weather", new PriceSet([Price.For(KnownAssets.EurcBaseSepolia, 0.01m)])));

app.MapGet("/weather", () => Results.Ok(new { City = "Brussels", Temp = 19 }));
app.Run();

  4. Pay for it from any .NET client

    The signer is the only place a key exists. Bring your own IPaymentSigner for an HSM or a KMS.

    dotnet add package Atypical.X402.Client
    using Microsoft.Extensions.DependencyInjection;
using X402.Assets;
using X402.Client;
using X402.Client.DependencyInjection;
using X402.Client.Signing;
using X402.Networks;

var myPrivateKey = Environment.GetEnvironmentVariable("X402_PRIVATE_KEY")
    ?? throw new InvalidOperationException("Set X402_PRIVATE_KEY before running.");

var services = new ServiceCollection();
services.AddX402Client(options =>
{
    options.AllowedNetworks.Add(KnownNetworks.BaseSepolia);
    options.SetLimits(KnownAssets.EurcBaseSepolia, perRequest: 1m, perSession: 10m);
});
services.AddSingleton<IPaymentSigner>(new PrivateKeyPaymentSigner(myPrivateKey));
services.AddHttpClient("PaidApi", c => c.BaseAddress = new Uri("http://localhost:5000"))
    .AddX402Payment();

var http = services.BuildServiceProvider()
    .GetRequiredService<IHttpClientFactory>().CreateClient("PaidApi");

try
{
    var response = await http.GetAsync("/weather"); // 402 -> sign -> replay -> 200, if the wallet can pay
}
catch (PaymentRejectedException)
{
    // Expected here with a fresh, unfunded wallet — the facilitator refuses settlement. Step 4
    // above is where a reader actually watching this succeed should start; see
    // samples/README.md#running-fully-offline for the real, unedited output.
}

    "Step 4" in that comment refers to the README's offline run. The runnable samples, PaidApi and PayingAgent, add dynamic per-request pricing, the facilitator probe, and real, unedited console output from actual runs.

Non-custodial by construction

The server holds nothing and signs nothing. That is enforced by what the code cannot express, not by a line in the documentation.

  • Atypical.X402.AspNetCore references no signing library.
  • X402Options exposes no key, secret or mnemonic property, so no operator can configure custody by accident. A test asserts that none appears.
  • Gas sponsoring, batching and custody are facilitator concerns. Adding a signing dependency to the server package would supersede ADR 0003; it must not happen quietly.

Limits of what’s proven here

A library that wants to be a reference implementation earns it by naming its own edges.

  • No published conformance vector suite exists.

    The x402 Foundation does not publish a cross-language test-vector corpus. This project’s vectors are extracted mechanically from JSON examples in the vendored specification documents, with provenance recorded in vectors/SOURCE.md. They are the most authoritative fixed data available, not an official suite.

  • No test reaches an on-chain failure mode.

    The test kit’s FakeFacilitator performs real EIP-712 signature recovery and real validity-window, amount and recipient checks, but it has no ledger. Insufficient balance, a reverted transferWithAuthorization, mempool races, or a facilitator reporting success on a transfer that later fails are all outside what any test here can catch.

  • There is no automatic adaptation to a facilitator’s capabilities.

    GetSupportedAsync is public surface on IFacilitatorClient, but nothing in the server or client package consults it to adjust which assets are offered or accepted. That decision is left to the operator, typically informed by running --probe once against the chosen facilitator.

  • The in-memory test server is more forgiving than a real transport.

    TestServer tolerates wire-level inconsistencies, such as a stale Content-Length, that a real Kestrel connection rejects. One such defect was found and fixed; the same blind spot could still hide an equivalent one elsewhere in the suite.
